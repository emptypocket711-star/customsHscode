# Marketplace Bid Revision Policy

작성일: 2026-06-03

## 현재 MVP 결정

현재 MVP에서는 파트너가 제출한 견적을 직접 수정하거나 철회하는 기능을 열지 않는다.

현재 제공 범위:

- 파트너는 매칭된 공개 요청에 견적을 1회 제출한다.
- 이미 제출한 활성 견적이 있으면 중복 제출 form을 숨긴다.
- 화주는 받은 견적을 제출 시점 조건으로 비교한다.
- 운영 상세와 개선 프롬프트는 견적 금액, 메시지 원문, 파일명, 개인정보 없이 상태와 정책만 표시한다.
- 조건 변경은 운영 확인 후 별도 처리 안내로 둔다.

## 이유

- 견적은 화주 선택, 파트너 알림, 완료 리포트, 후기 신뢰 지표와 연결된다.
- 파트너가 제출 후 금액이나 조건을 직접 바꾸면 화주가 비교한 조건과 실제 진행 조건이 달라질 수 있다.
- 철회 기능은 화주가 이미 선정했거나 진행 중인 거래와 충돌할 수 있다.
- 따라서 수정/철회는 단순 UI 버튼이 아니라 상태 전이, 감사 로그, 상대방 알림, 운영 확인 정책이 함께 필요하다.

## 현재 안전장치

- `service_bids_one_active_bid_per_partner_idx`는 같은 요청·파트너 조합에 활성 견적 1개만 허용한다.
- `submit_freight_bid`와 `submit_clearance_bid` RPC는 기존 활성 견적이 있으면 `이미 제출 중인 견적이 있습니다.` 예외를 발생시킨다.
- 클라이언트에는 직접 `service_bids` insert/update 정책을 열지 않는다.
- 입찰 제출과 선정은 RPC를 통해서만 처리한다.
- 사용자 화면에는 수정·철회 직접 처리 불가 정책을 표시한다.

## 나중에 수정 기능을 열 때 필요한 조건

수정 기능은 아래 조건이 모두 충족될 때만 검토한다.

- 요청 상태가 `open` 또는 `bids_received`이다.
- 해당 견적 상태가 `submitted` 또는 `shortlisted`이다.
- 견적이 아직 `selected`가 아니다.
- 마감 시간이 지나지 않았다.
- 수정 전후 금액, 유효기한, 리드타임, 메시지 변경 이력이 audit log에 남는다.
- 화주에게 “견적 조건 변경됨” 알림이 간다.
- 화주 화면에는 기존 제출일과 최근 수정일이 함께 표시된다.

권장 RPC:

- `revise_freight_bid(...)`
- `revise_clearance_bid(...)`

직접 table update 정책은 열지 않는다.

## 나중에 철회 기능을 열 때 필요한 조건

철회 기능은 아래 조건이 모두 충족될 때만 검토한다.

- 요청 상태가 `open` 또는 `bids_received`이다.
- 견적 상태가 `submitted` 또는 `shortlisted`이다.
- 견적이 아직 `selected`가 아니다.
- 철회 후 요청에 남은 견적 수와 화주 다음 행동 안내가 갱신된다.
- 철회 사유가 짧은 코드 또는 메모로 저장된다.
- 화주와 운영자에게 철회 상태가 민감 원문 없이 표시된다.

권장 RPC:

- `withdraw_service_bid(p_bid_id uuid, p_reason text)`

## 금지

- 파트너가 `service_bids`를 직접 update/delete 하게 하지 않는다.
- 선정된 견적을 파트너가 직접 수정하거나 철회하게 하지 않는다.
- 진행중 또는 완료 거래의 견적 조건을 일반 수정 기능으로 바꾸지 않는다.
- 운영 상세와 개선 프롬프트에 견적 메시지 원문, 파일명, 단가 원문, 개인정보를 포함하지 않는다.

## 다음 구현 순서

1. 수정/철회 정책을 운영자 검토 기능으로 먼저 둘지 결정한다.
2. 철회 사유 코드와 audit event 이름을 정의한다.
3. RPC와 RLS 테스트를 먼저 작성한다.
4. 파트너 화면에는 selected 전 상태에서만 버튼을 노출한다.
5. 화주 화면에는 변경/철회 상태를 비교 카드에 표시한다.
6. 운영 상세에는 원문 없이 상태와 건수만 표시한다.
